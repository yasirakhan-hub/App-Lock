SECTION A: EXISTING PROJECT ARCHITECTURE
================================================================================

Smart AppLock is engineered using a clean, layered native Android architecture
divided into five primary subsystems:

1. JETPACK COMPOSE UI LAYER
   - MainActivity (FragmentActivity):
     Houses the root NavHost with animated crossfades managing high-level screen states:
     * AUTH_GATE: Master gatekeeper requiring PIN or BiometricPrompt to access configuration.
     * ONBOARDING: First-time setup flow (Welcome -> Create PIN -> Confirm PIN -> Recovery -> Biometrics).
     * DASHBOARD: Main status hub displaying monitoring status, quick protection toggle, system permission health cards, theme switch, and navigation.
     * APP_SELECTION: Installed applications viewer with search filtering, protected app toggles, and authentication challenges.
     * SETTINGS: Complete security preferences, PIN changes, recovery question changes, relock policies, Device Admin management, and About section.
     * TEST_LOCK: In-app simulation environment allowing users to safely test lock screen behavior.
   - LockActivity (FragmentActivity):
     Fullscreen overlay activity executed with taskAffinity="" and excludeFromRecents="true".
     Launched over protected apps upon foreground detection. Supports BiometricPrompt and numeric PIN entry.

2. SHARED UI & REUSABLE COMPONENTS
   - AuthChallengeDialog:
     Reusable modal dialog gating sensitive operations (protecting apps, changing credentials, deactivating Device Admin, clearing data) behind biometric or PIN verification.
   - PinKeypad & PinDots:
     Accessible, haptics-enabled keypad supporting 4-digit or 6-digit PINs, lockout state visualization, backspace deletion, and quick biometric re-trigger.

3. REPOSITORY & DOMAIN CONTROLLER LAYER
   - AppLockManager (Singleton):
     Central engine coordinating foreground package detection, session-authenticated package sets (unlockedPackages), target intent caching (pendingInterceptedTargets), debounce timing (600ms), and home launcher package caching.
   - AppDiscoveryRepository:
     Queries installed applications using packageManager.queryIntentActivities for Intent.ACTION_MAIN + CATEGORY_LAUNCHER. Caches application labels, critical system classifications, and app icon ImageBitmaps.
   - PermissionHelper & DeviceAdminHelper:
     Manages system permission detection (Accessibility, Overlay, Usage Stats, Device Admin) and launches corresponding platform settings intents.

4. FOREGROUND INTERCEPTION & SYSTEM LIFECYCLE
   - AppLockAccessibilityService:
     Native AccessibilityService listening for TYPE_WINDOW_STATE_CHANGED events.
     Configured with canRetrieveWindowContent="false" for strict zero-read privacy.
     Contains anti-force-stop detection (intercepting Settings -> App Info navigation) and anti-uninstall protection.
   - AppLockDeviceAdminReceiver:
     DeviceAdminReceiver enforcing BIND_DEVICE_ADMIN. Intercepts onDisableRequested to display security warning dialog.
   - ScreenReceiver:
     Dynamically registered broadcast receiver listening for Intent.ACTION_SCREEN_OFF to clear temporary session unlocks when the user locks their device.
   - BootReceiver:
     Broadcast receiver listening for Intent.ACTION_BOOT_COMPLETED to ensure system initialization after device restart.

5. DATA PERSISTENCE & CRYPTOGRAPHIC SECURITY
   - AppLockPreferences:
     Local storage via SharedPreferences ("secure_applock_prefs") backed by in-memory volatile caches for sub-microsecond package lock checks.
   - PinHashUtil:
     Cryptographic helper employing PBKDF2 / SHA-256 with 5,000 hash stretching rounds, 16-byte random salts, and MessageDigest.isEqual constant-time equality comparisons to prevent timing attacks.

SECTION C: CRITICAL BUGS, SECURITY RISKS, AND PLATFORM LIMITATIONS
================================================================================

1. ANDROID SYSTEM BOUNDARIES: DEVICE ADMIN VS DEVICE OWNER
   - On Android 10+ (API 29+), standard DeviceAdminReceiver does not grant third-party
     apps the authority to block the OS Settings "Force Stop" button or completely
     prohibit uninstallation.
   - Genuine uninstallation prevention is strictly restricted to Device Owner (MDM) mode,
     which must be provisioned during initial device factory setup via NFC, QR code, or ADB.
   - Implementation Resolution:
     Smart AppLock utilizes an effective hybrid approach:
     a) AccessibilityService detects window transitions into Settings -> App Info for
        com.aistudio.applock.secjkv and immediately sends GLOBAL_ACTION_HOME.
     b) AppLockDeviceAdminReceiver implements onDisableRequested() to prompt a warning.
     c) The application clearly discloses this system boundary in its "Technical Architecture
        & Limits" dialog to maintain complete honesty and user trust.

2. AGGRESSIVE OEM BATTERY KILLERS & SERVICE TERMINATION
   - Manufacturers such as Xiaomi (MIUI/HyperOS), Samsung (One UI), Huawei (EMUI), and
     Oppo/Realme (ColorOS) employ non-standard battery optimization daemons that kill
     background AccessibilityServices when apps are idle.
   - Implementation Resolution:
     The app features setup verification cards and permission helpers directing users
     to disable battery optimization for Smart AppLock ("Unrestricted Battery" / "Autostart").

3. ANDROID 12+ (API 31+) BACKGROUND ACTIVITY LAUNCH RESTRICTIONS
   - Android 12 severely restricts launching activities from the background (e.g. from
     background services or broadcast receivers).
   - Implementation Resolution:
     Smart AppLock bypasses this constraint legitimately by launching LockActivity directly
     from the active AppLockAccessibilityService context (which holds the foreground window token)
     combined with Intent.FLAG_ACTIVITY_NEW_TASK and the SYSTEM_ALERT_WINDOW permission.

4. ACCESSIBILITY PRIVACY & GOOGLE PLAY POLICY COMPLIANCE
   - Accessibility services that read screen contents are subject to strict scrutiny on Google Play.
   - Implementation Resolution:
     Smart AppLock explicitly configures accessibility_service_config.xml with:
     * canRetrieveWindowContent="false"
     * accessibilityFeedbackType="feedbackGeneric"
     * accessibilityEventTypes="typeWindowStateChanged"
     This guarantees the service cannot read user keystrokes, personal messages, or screen data.
